# 1. Purpose

This document defines the official database architecture, schema conventions, migration strategy, indexing standards, and data modeling rules for the 7Oz Espresso Cafe Digital Platform.

All database changes must comply with this document.

---

# 2. Database Philosophy

The platform adopts a **Database-First** approach.

Principles:

- PostgreSQL is the source of truth.
- Schema changes are performed exclusively through migrations.
- sqlc generates type-safe Go code from SQL queries.
- Repositories interact only through generated queries.
- Automatic schema synchronization is prohibited.

---

# 3. Database Engine

Engine

- PostgreSQL

Character Encoding

- UTF-8

Timezone

- UTC

Collation

- Default PostgreSQL collation

---

# 4. Migration Strategy

Migration tool

- golang-migrate

Rules

- One logical change per migration.
- Never edit an applied migration.
- Create a new migration to modify existing schema.
- Every migration must support rollback whenever possible.

Migration filenames:

```
YYYYMMDDHHMMSS_description.up.sql
YYYYMMDDHHMMSS_description.down.sql
```

# 5. Naming Conventions

Tables

- snake_case
- plural nouns

Examples:

- users
- reservations
- menu_items
- loyalty_transactions

Columns

- snake_case

Primary Keys

- id

Foreign Keys

- <table>_id

Examples:

- user_id
- reservation_id
- membership_id

Indexes

idx_<table>_<column>

Unique Constraints

uq_<table>_<column>

Foreign Keys

fk_<table>_<referenced_table>

---

# 6. Primary Keys

All tables use UUID.

Example:

id UUID PRIMARY KEY

UUIDs are generated by the application layer.

Do not use auto-increment integer IDs.

---

# 7. Audit Columns

Every business table should include:

- created_at
- updated_at

Soft-deletable tables additionally include:

- deleted_at

Timestamp type

TIMESTAMPTZ

---

# 8. Soft Delete Policy

Use soft delete only for business entities that require historical recovery.

Examples:

- users
- memberships
- menu_items

Avoid soft delete for transactional or immutable records such as:

- loyalty_transactions
- audit_logs

---

# 9. Relationships

Use foreign key constraints whenever appropriate.

Avoid storing duplicated business data.

Normalize to at least Third Normal Form (3NF) unless a justified denormalization improves performance.

---

# 10. Indexing

Create indexes for:

- Foreign keys
- Frequently filtered columns
- Frequently sorted columns
- Search fields
- Unique identifiers

Review query plans before adding additional indexes.

---

# 11. Transactions

Business transactions belong in the Service layer.

Database transactions should:

- Be short-lived.
- Roll back on failure.
- Never span external services.

---

# 12. SQL Standards

All SQL queries must:

- Explicitly list columns.
- Avoid SELECT *.
- Use parameterized queries.
- Be readable and consistently formatted.

---

# 13. sqlc

Directory structure:

database/
├── migrations/
├── queries/
└── sqlc/

Each module owns its own query file.

Examples:

queries/
├── reservation.sql
├── membership.sql
├── loyalty.sql
├── menu.sql
└── users.sql

Generated code must never be edited manually.

---

# 14. Constraints

Use constraints to protect data integrity.

Examples:

- NOT NULL
- UNIQUE
- CHECK
- FOREIGN KEY

Business rules should not rely solely on application validation.

---

# 15. Performance

Optimize for:

- Readability
- Correctness
- Predictable query plans

Avoid premature denormalization.

Measure before optimizing.

---

# 16. Backup & Recovery

Production deployments must support:

- Scheduled backups
- Point-in-time recovery (future)
- Restore validation

Backups must be tested periodically.

---

# 17. AI Development Rules

AI agents must:

- Create migrations for every schema change.
- Never modify applied migrations.
- Never write SELECT *.
- Always use parameterized SQL.
- Reuse existing query files where possible.
- Respect naming conventions.

---

# 18. Definition of Done

Database work is complete only if:

✓ Migration created

✓ Rollback provided

✓ Constraints applied

✓ Indexes reviewed

✓ sqlc generation successful

✓ Documentation updated

✓ No breaking schema changes introduced without approval
